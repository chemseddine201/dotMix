## 3. Deep-Dive on Canonical Conflicts & Proposed Resolutions

### 3.1 Keyed List Reconciliation & Duplicate Keys (D-110 vs v3.2.2 R-KEY-03)
- **Authoritative Guardrail (`ARCHITECTURE_GUARDRAILS.md` §H):**
  > *"Stable keys and deterministic behavior. Duplicate keys produce deterministic diagnostics. **No synthetic/surrogate fallback keys to conceal duplicates.** Avoid creating DOM/Owner state for a duplicate item that is rejected."*
- **Authoritative Decision (`governance/DECISION_REGISTER.md` D-110):**
  > *"No surrogate fallback keys; deterministic duplicate-key diagnostics and atomic behavior. Verify duplicate item is rejected before DOM/Owner creation where feasible."*
- **The Conflict in `spec/MIX_SPEC_v3.2.2.md` §7 (R-KEY-03):**
  > *"R-KEY-03 (الإنتاج): يُمنع حذف أي عنصر. التكرار رقم n للمفتاح k يأخذ هوية داخلية (k, n)، ويُعرض كل العناصر مع تحذير onWarning."*
- **Proposed Ratified Policy (Submitted for Approval):**
  Adopt the **Atomic Duplicate-Update Rejection Policy**:
  1. Validate the complete incoming collection of keys upfront before diffing.
  2. Detect duplicate keys deterministically.
  3. Reject the invalid update atomically.
  4. Preserve the previously rendered collection intact.
  5. Do not allocate DOM nodes or owner instances for items in an invalid update.
  6. Emit a deterministic diagnostic (`MIX_ERR_DUPLICATE_KEY`) in both development and production.

### 3.2 Dynamic Element Syntax (D-105 vs Historic Proposal)
- **Authoritative Charter (`governance/PROJECT_CHARTER.md` §4):**
  > *"The approved dynamic element syntax baseline is: `<{~expr}>...</{~expr}>`. The `~` marker is canonical in the currently approved baseline and must not be removed or altered without explicit approval."*
- **Historic Agent Deviation in `reports/phase-0-audit.md`:**
  The previous agent had recommended Option A (`<{expr}>`) without the tilde. The Project Charter has decisively overridden that recommendation and locked `<{~expr}>`.

### 3.3 Trusted HTML Boundary & Sanitizer Authority (D-109)
- **Coexistence Model:**
  `SanitizerProvider` and a module-scoped `WeakSet` registry coexist cleanly:
  1. `SanitizerProvider` defines the approved application-level sanitization authority (`setSanitizerProvider`).
  2. `createTrustedHtml(dirtyHtml)` invokes that authority.
  3. A private module-scoped `WeakSet<object>` records authentic trusted instances.
  4. The HTML sink accepts only registered objects from the `WeakSet`.
  5. Native W3C Trusted Types integration is used where supported.
- **Vulnerability in Previous v3.2.2 Draft:**
  `createTrustedHtml(dirtyHtml, sanitizerFn)` allowed the caller to supply an arbitrary sanitizer function (such as an identity function `x => x`), bypassing security.
- **Ratification:** The sanitizer authority must be controlled strictly by the approved application-level security boundary, not freely supplied by component code.
